### 四、发布过程与一次真实失败（都留了痕）

1. `git tag -a v0.2.0`，`node scripts/verify-release.mjs` → `✅ 发布前置检查通过：dsh-ponytail-58fly@0.2.0，tag v0.2.0 已就位`；`git push origin main` + `git push origin v0.2.0`。
2. **首跑失败（run 42404759248）**：publish job 14s 红在 `pnpm test`，`# tests 23 / # pass 5 / # fail 18`，逐字 `Cannot find module …/lib/l0/within.js`。根因：`lib/` 是构建产物且被 .gitignore 排除，CI 干净检出里不存在，而 16 个测试文件从 `../lib/` 导入。本地能过只因为本机 `lib/` 一直在。
3. **修法（commit b0bf92f）**：删掉 publish.yml 里那一步 `pnpm test` —— 它不是漏了 build，而是**本来就不该单跑**：`prepublishOnly` 第七道门已经在 `build` 之后跑过全套 221 条。删比加更对：加 build 会让同一件事跑两遍，且掩盖「测试依赖产物」这个真实形状。
4. **重跑成功（run 42405055528，workflow_dispatch）**：七道门逐条绿，`npm publish` 输出 `Publishing to https://registry.npmjs.org/ with tag latest and public access` / `+ dsh-ponytail-58fly@0.2.0`。
5. 发布瞬间 registry 先只显示占位版本 `0.0.0-stage`（`dist-tags.latest = 0.0.0-stage`），约 40s 后才变 `latest = 0.2.0`。**首包都有这个传播窗口，不是失败。**

### 五、真发现（票面没预见的）

1. **本地 `lib/` 的存在会掩盖 CI 失败** —— 任何「测试从构建产物导入」的仓库，CI 里 test 必须在 build 之后。这条是首跑失败暴露出来的，与发布本身无关，但只有真发布才撞得到。
2. **`gh workflow run <文件名>` 不可靠，按 workflow id dispatch 才稳** —— 实际用的是 `gh api -X POST repos/58fly/dsh-ponytail-58fly/actions/workflows/410562969/dispatches -f ref=main`（publish 是 410562969，ci 是 410562968）。
3. **首包的 `dist-tags.latest` 有传播窗口** —— 发布成功后 30–60s 内 `latest` 可能还停在 `0.0.0-stage`。任何「发完立刻查 latest」的自动化都要容忍这段。
4. **`0.0.0-stage` 是个永久占位版本** —— registry 的 `versions` 里它一直在，`verify-release.mjs` 用 `NPM_INTERNAL_VERSIONS = new Set(['0.0.0-stage'])` 豁免它，否则「每个已发布版本都要有 tag」这条会永远红。

### 六、遗留：`verify-release` 现在红（真实告警，不属本票未完成）

```
$ node scripts/verify-release.mjs
❌ 发布校验失败（1 项）
  - tag v0.2.0 之后有 2 个进包文件变化：README.md、package.json
    → 进包内容变了就必须升版本、重新打 tag；只改不进包的文件不需要
```

- **成因**：02 与 03 两张票在 `v0.2.0` 之后改了 `README.md`（补发布后命令、发布卡口第四行）与 `package.json`（加一行 `verify:published` 脚本）。这两者都在 `files` 白名单里。
- **为什么不是本票的问题**：registry 上 0.2.0 的字节与 tag 时的字节**一致**（shasum 三方核对过），历史事实没被破坏。脚本报的是「下一次发布前得先升版本」，而不是「已经发错了」。
- **处置**：发 `0.2.1`（把这两处文档/脚本改动归进它），或在下一次发布前让 tag 追上。**不在本票范围内**，因为本票的交付（0.2.0 真在 registry 上、可装可用、字节可核）已经达成；为了让脚本变绿而重打 `v0.2.0` tag 才是错的——那会让一个已发布的版本换一份 commit。
