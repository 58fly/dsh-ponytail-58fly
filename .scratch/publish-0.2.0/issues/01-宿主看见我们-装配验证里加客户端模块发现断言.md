# 01: 宿主看见我们：装配验证里加客户端模块发现断言

**What to build:** 跑一次装配验证，就能看到**宿主自己给出的判定**：它把本包认成网页平台的客户端模块、给出一个真实存在的客户端产物路径、模块图里有本包这一行。宿主没认的时候要按四种成因分别说清是哪一种，而不是只报一句断言失败。删掉客户端声明、把平台改成别的、删掉导出映射里的客户端入口——这三种破坏各让检查变红；恢复原样重新变绿。

## Answer

装配验证现在会问宿主自己：`assemble` 形态跑完既有五段之后，多出一段「宿主判定」，六行输出全部来自 `ClientModuleRegistry` 的公开面，不是自查声明文本。

### 票面假设被实测修正的两处

1. **「结果里平台是网页」这条无法从返回值读。** `resolveMeta` 返回 `{packageName, meta:{clientPath, manifestPath, inject, external, immediately}}` —— 没有 `platform` 字段。平台在宿主内部只当门禁用（`platform !== "web"` 就返 `null`），返回值里根本不携带。所以这一项改成「`resolveMeta` 返回非空」的间接证明，并在输出里写明这层推理；反向自检把平台改成 `node` 时它必须变红，这就是该证明的证伪面。
2. **靠「把插件装进树再看 `graph().entries`」在探针里本来是空的。** 根因是 `@deepseek-ai/cordis-plugin-include` 会把子树 `baseUrl` 改成 `cordis.yml` 所在目录（`dsh-app-boot/lib/index.js:739-743`），而宿主解析包名是从那个 baseUrl 出发的。原来的装配探针把 `cordis.yml` 写进临时 home，那里没有 `node_modules`，宿主必然解析不到本包 —— **这不是「宿主没认我们」，是探针自己给错了目录。** 改成写进 profile 目录（= 真宿主的 profile 形态：`cordis.yml` 与 `node_modules` 同层）之后，`graph().entries` 才有本包这一行。

### 顺带发现（票面没预见）

1. **装载器之后挂登记服务是硬顺序，不是风格。** `ClientModuleRegistry` 构造函数里 `for (const entry of ctx.loader.entries()) this.dirty.add(entry.options.name)` 紧接 `compose()` + `flush()`；挂早了 `ctx.loader` 还不存在，挂成之后 `internal/plugin` 事件也不会回溯补偿已装好的 entry。
2. **`flush` 自己也是一次 `queueMicrotask`，`await loader.await()` 之后必须再等一拍**，否则 `graph()` 可能仍是空的。探针等 200ms（一次 microtask 不够，200ms 足够且不显著拖慢）。
3. **selftest 副本化必须无条件做，不能只判软链。** tarball / assemble 形态下 pnpm 把文件硬链接到全局 store，直接改 manifest 会把 store 里那份一起污染，别的 profile 跟着坏。
4. **`resolveMeta` 对「声明了 `dsh.client` 却拿不到 `exports["./client"]`」是抛错而不是返 null**，所以两条失败路径都要接到同一句分类文案上，否则用户看到的是一句宿主内部异常，看不出是自己清单写错了。
