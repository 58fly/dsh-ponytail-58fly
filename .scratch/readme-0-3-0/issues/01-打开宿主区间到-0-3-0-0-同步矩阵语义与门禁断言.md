# 01: 打开宿主区间到 0.3.0-0，同步矩阵语义与门禁断言

**What to build:** 

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] `pnpm run check:matrix` 在新区间下退出码 0，输出「覆盖区间内全部 15 个版本」。
- [ ] `pnpm run verify` 全绿，不再出现 `<0.2.3-0` 形态的失败提示。
- [ ] 矩阵里人为插入一格未发布版本时，报错信息明确说「该版本尚未发布」，而不是「区间外」。
- [ ] 区间判定单测覆盖 `0.2.99`（在内）与 `0.3.0-0` / `0.3.0`（在外），`pnpm test` 全绿。
- [ ] 全局搜 `0.2.3-0` 只剩历史记录（CHANGELOG、docs/releases）中的出现，脚本与配置里零命中。

## 要交付什么

装本插件的人，在宿主 0.2 线任何一个未来的 patch / minor 版本上，都不会再被 `incompatible-version` 挡住；同时发布的七道门在新区间下仍然全绿、且能拦住「矩阵预填了还没发布的版本」这条新反例。

这是全案唯一改动发布产物对外声明的一刀，先单独落地，其余七张票都建立在它之上。

## 已实测的事实（建票前跑过真仓库）

- 把 `engines.dsh` 改成 `>=0.2.0-rc.1 <0.3.0-0` 后跑 `check:matrix`：15 个版本全绿、退出码 0。**不需要**「未发布版本打印 SKIP」这类正向分支——`expected` 是从 registry 全集过滤出来的，未发布版本根本不在全集里。
- 只改 `engines.dsh` 跑 `verify`：直接红，原话 `engines.dsh 必须是 >=0.2.0-rc.1 <0.2.3-0 形态`。这道断言硬编码了旧上界，是打开区间唯一必须同步改的脚本。
- 手动在 CI 矩阵里插一格未发布的 `0.2.3` 再跑 `check:matrix`：红在 `矩阵里有区间外的版本：0.2.3`。真正需要放行的反例是「预填了未来格」，提示语却说的是「区间外」，两者在打开上界后会混淆。
- `satisfiesRange` 的边界实测：`0.2.0-rc.1` / `0.2.2-rc.1` / `0.2.99` / `0.2.3` 在内，`0.3.0-0` / `0.3.0` / `1.0.0` 在外。

## 要做的四件事

1. `package.json#engines.dsh` 改为 `>=0.2.0-rc.1 <0.3.0-0`。
2. 发布校验脚本里那条硬编码 `<0.2.3-0` 的断言：改成对新区间的判定，提示语同步改写，保留原本「这是唯一版本闸门」的理由说明，但不再声称「`<0.2.3-0` 才能排除 0.3.0 系列」。
3. 矩阵校验脚本的 `extra` 反例提示语：区分「超出了 `engines.dsh` 区间」与「区间内但该版本尚未发布」两种情况，后者提示语要写明「宿主还没发这个版本，先别预填格」。判红逻辑不变。
4. 给区间判定补一条纯函数单测，覆盖上面那组边界（尤其 `0.2.99` 在内、`0.3.0-0` 与 `0.3.0` 在外）。

## 不做

- 不改运行时代码，不改技能正文与 `skills/UPSTREAM.json`。
- 不预填任何未来版本的矩阵格。
- 不把上界抬到 `<1.0.0-0`。
- 不动 CI 矩阵里已有的 15 格（它们本来就该在）。
