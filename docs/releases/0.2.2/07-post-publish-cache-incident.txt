=== 0.2.2 发布后撞到的第一件事：npm 本地缓存把「刚发成功」报成「不存在」 ===

这一份记录的是**事实**，不是推演。发布 run 42440579889 是 success、registry 上 0.2.2 已经在，
但紧接着执行 `pnpm run verify:published` 时它连续四次退 1，报的是版本不存在。

--- 现场（逐字）---
$ node scripts/verify-published.mjs
  ...
  cmd: 'npm pack dsh-ponytail-58fly@0.2.2 --json --pack-destination /var/folders/.../pt-published-N4imPL',
  stdout: '{"error": {"code": "ETARGET", "summary": "No matching version found for dsh-ponytail-58fly@0.2.2."}}',
  stderr: 'npm error code ETARGET
          npm error notarget No matching version found for dsh-ponytail-58fly@0.2.2.',
  → 退出码 1，还附带了 execFile 的整个错误对象（含 stack），读起来像脚本自己崩了。

同一时刻：
  $ npm view dsh-ponytail-58fly@0.2.2 dist --json   → 成功，attestations 都在
  $ npm view dsh-ponytail-58fly dist-tags --json    → {"latest":"0.2.2"}
→ registry 是好的，是**本地**这一侧解析不到。

--- 成因 ---
npm 的 packument 缓存带 stale-while-revalidate：`npm view` 会先回缓存再后台刷新，
而 `npm pack` 按同一份旧 packument 解析版本号，于是「包有这个版本」在 view 里已经可见，
在 pack 里还看不见。两者读的是同一份缓存的两个时刻，所以会自相矛盾。

验一下缓存里确实有这些条目（发布前写的）：
$ npm cache ls dsh-ponytail-58fly
  make-fetch-happen:request-cache:https://registry.npmjs.org/dsh-ponytail-58fly
  …（另有 0.2.0 / 0.2.1 / 0.2.2 三份 tgz 条目）

--- 修法（两处，都在 scripts/ 里，不进包）---
1. 读 registry 的两条命令一律加 `--prefer-online`：
     npm view <name>@<ver> dist --json --prefer-online
     npm pack <name>@<ver> --json --pack-destination <dir> --prefer-online
   让包管理器自己去核对上游，而不是在脚本里猜缓存何时过期。
2. 把 ETARGET 单独归类（新函数 classifyUnpackable），并且接住 pack 的错误只打一句结论：
     ETARGET = 「有这个包、没有这个版本」（多半是缓存）；
     E404    = 「registry 上没有这个东西」（真的没发）；
     npm 11 还会写成小写 notarget No matching version found（没有 ETARGET 字样），
     所以除了错误码也认这句人话。

--- 修完的实测（同一条命令，同一个版本）---
$ node scripts/verify-published.mjs
发布后复验：dsh-ponytail-58fly@0.2.2
registry 记录：shasum=45af2658f7506024a307f570c9aee2bf79fc71fa integrity=sha512-wD5OkGHDfeAG2[…]
产地签名：SLSA provenance 已签名（https://slsa.dev/provenance/v1）
下载并核对：dsh-ponytail-58fly-0.2.2.tgz  92709 字节  shasum=45af2658…  integrity 也一致 ✓
  …（技能面 / 四档体量 / 宿主判定六行）
✅ 复验通过：dsh-ponytail-58fly@0.2.2 从 registry 拉回的真字节可装可用
退出码：0

--- 为什么这不算 0.2.2 的缺陷 ---
出问题的是**读 registry 的脚本**，不是发出去的那 60 个文件。`scripts/` 不在 `files` 白名单里，
所以 registry 上 0.2.2 的 tarball 与发布那一刻逐字相同（shasum 45af2658… 已用三方核过）。
修复跟着下一个版本走，不需要重发 0.2.2。

--- 留给后面的人 ---
任何「发布后立刻读 registry」的脚本都要考虑这条：写完立刻读，读到的不一定是刚写的那份。
这不是 npm 的 bug，是缓存策略的必然结果；能做的只有让读的那一步显式要求新鲜数据。
