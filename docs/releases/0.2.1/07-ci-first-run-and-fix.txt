--- 二、根因 ---

「宿主 undefined」不是探针取错了路径，是老宿主根本没有这个字段。
逐版本把 @deepseek-ai/dsh-client-modules 拉下来 grep manifestPath 出现次数，
结果是干净的分水岭：

  0.2.0-rc.1    0 命中      0.2.1-rc.1    0 命中
  0.2.0-rc.2    0 命中      0.2.1-rc.2    0 命中
  0.2.1-alpha.1 0 命中      0.2.1-rc.3    0 命中
  0.2.1-alpha.2 0 命中      0.2.1-rc.4    0 命中
  0.2.1-alpha.3 0 命中      0.2.1-rc.5    0 命中
  0.2.1-alpha.4 0 命中      0.2.2-alpha.2 2 命中
  0.2.1-alpha.5 0 命中      0.2.2-alpha.3 2 命中
                            0.2.2-rc.1    2 命中

旧版 resolveMeta 返回的 meta 只有 {clientPath, inject?, external, immediately}；
新版才多一个 manifestPath（它同时被 fetchBundle 用来 createRequire 定位包内资源）。
而我们这条断言是「宿主读的 manifest 是不是包里那一份」——
问的是一件老宿主压根不回答的事。拿 undefined 去比，等于把整个旧区间判红。

--- 三、修法（commit 704ea01）---

只在宿主真给了路径时判定归属，没给就跳过：

  const hostManifest = resolved.meta.manifestPath;
  if (checkProvenance && typeof hostManifest === 'string' && hostManifest !== realManifest) {
    throw new Error('宿主读的 manifest 不是包内那一份：宿主 ' + hostManifest + '，包内 ' + realManifest);
  }

返回值里记成 manifestPath: typeof hostManifest === 'string' ? hostManifest : null，
不把 undefined 冒充成「查过了」。

--- 六、这次事故的教训 ---

1. 探针问宿主的每一个字段都要先确认「这个字段在其声称支持的区间里都真的存在」。
   engines.dsh 写的是 >=0.2.0-rc.1 <0.2.3-0，那就得按整个区间验，不能只按最新宿主验。
2. 本地全绿掩盖不了这件事：本机装的是 0.2.2-rc.1，落在有新字段的那一半。
   只有 compat 矩阵会把它逼出来 —— 这就是那 15 个格子存在的意义。
3. 修复本身不进包（scripts/ 不在 files 白名单），所以 verify-release 的
   「tag 之后进包内容不得变化」不会红；这一点已实测（GATE7=0）。
