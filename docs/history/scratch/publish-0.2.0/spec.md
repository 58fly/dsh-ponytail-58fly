# 规格：把 dsh-ponytail-58fly 0.2.0 发出去，并让「宿主看得见我们」成为机器证据

Status: resolved

## Problem Statement

从使用者与维护者两个视角看，现在缺的是三件事，都不是功能。

**一、这东西在 npm 上不存在。** 包已经打完（六十个文件、六道质量门全绿），但在 registry 上查是 404。任何想用它的人只能从一个本地文件拷走一个压缩包，没有版本号可引用、没有升级路径、没法写进依赖清单。地图的 Destination 第一条写的是「在干净的宿主上可直接安装启用」——「可直接安装」在使用者语言里意味着按包名安装，不是按文件路径安装。

**二、「装完之后设置页真的多出那一栏吗」没有观察证据。** 当前证据链止于三层推断：清单里客户端声明形状对、产物里真的往设置页槽位注册了、声明与源码两侧互相印证。这三条合起来能排除「我们写错了」，排除不了「宿主在别处把我们丢了」：模块图排序、设置页槽位的声明方缺席、权限不足导致整块界面静默消失，这三条都在现有证据之外。使用者看到的仍然是「装了，没反应」。

**三、发出去的字节与本地打出来的字节，没有机器核对。** 现在只有一句人工比对的哈希。如果 registry 上的包与本地那份不同（打包机版本差异、忽略清单行为差异、某个打包钩子），没有任何一条检查会发现。

## Solution

三件，全部长在已有的验证装置上，不新造装置。

1. **把 0.2.0 发到 npm**，公开、MIT、默认标签指向它；发布命令只能经发布前钩子里的那六道门，不允许任何旁路写进文档。
2. **发布后从 registry 拉回来复验**：在一个干净目录里把 registry 上那份压缩包取下来，对它重跑装配验证（六个技能、切档渲染、用户目录零垃圾），并断言 registry 记录的完整性哈希与本地打包产出一致。这样「使用者真会装到的东西」第一次成为被验证的对象。
3. **给装配验证加一层「宿主看见我们」的证据**：在装配探针已经起好的那棵真 cordis 树里，挂上宿主自己的客户端模块登记服务，断言它把本包认成网页平台的客户端模块，并给出一个指向真实存在的客户端产物的路径。界面渲染与视觉验收明确不在这条线上——那是人眼的事，不假装能自动化。

做完之后，一个陌生人拿到的是：一句按包名安装的命令能装上的包，加上三条机器证据——「宿主发现了客户端入口」「客户端产物能往设置页注册」「卸掉之后用户目录里什么都不剩」。

## User Stories

### 安装者

1. 作为一个 DSH 使用者，我想用一行按包名的命令装上它，这样我不需要先找人要一个压缩包文件。
2. 作为一个 DSH 使用者，我想要的版本能写进配置并被锁定，这样团队里每个人装到的是同一份字节。
3. 作为一个 DSH 使用者，我想在装之前就能看到它的说明与许可，这样我不用先下载再判断。
4. 作为一个 DSH 使用者，我装完之后应该能在设置页看到 Ponytail 那一栏，这样我不用去翻文档确认它是否生效。
5. 作为一个 DSH 使用者，如果我所在的宿主版本比声明的区间新，我应该在安装时就被拒绝，而不是装出一个半坏的东西。
6. 作为一个只想用宿主侧功能的用户，我不装任何客户端界面也应该能通过斜杠命令切档，这样界面出问题不影响我干活。
7. 作为一个从旧包迁过来的用户，我想看到技能标识与命令前缀没变，这样我的肌肉记忆与既有笔记都还成立。
8. 作为一个在断网环境里部署的人，我需要知道离线安装这条路的边界在哪，这样可以提前备好压缩包而不是到现场才发现装不上。

### 维护者

9. 作为维护者，我发版时希望有一条命令能跑完六道门（类型检查 / 构建 / 产物校验 / 技能校验 / 兼容矩阵 / 测试），这样我不会因为漏跑一道而发出坏包。
10. 作为维护者，我希望发布命令无法绕过那六道门，这样「赶时间手动删一步」这个选项在流程上就不存在。
11. 作为维护者，我希望发完之后能立刻验证「使用者会装到的那份」是好的，而不是只验证「我本地打出来的那份」是好的。
12. 作为维护者，我希望有人改动客户端声明或注册姿势时检查会红，这样「装得上但装不进去」不会再次静默发生——这类问题已经发生过一次。
13. 作为维护者，我希望发布失败时能干净收场：版本号不前进、默认标签不被污染，这样一次失败不会变成一次尴尬的热修发版。
14. 作为维护者，我希望知道哪些动作是不可逆的、不可逆的窗口有多长，这样我在按下回车之前就知道退路在哪。
15. 作为维护者，我希望规格里写的每条断言都能被一条命令复现，而不是「我记得我跑过」。

### 持续集成与自动化

16. 作为维护流水线的人，我希望发布后的复验是一个能被反复执行的脚本而不是一段一次性命令，这样每次发版后都能重跑。
17. 作为维护流水线的人，我希望「宿主是否发现客户端入口」这条断言有一个反向用例（把声明删掉必须变红），这样绿灯不是装饰。
18. 作为维护流水线的人，我希望证明这条新断言在缺陷实现上会红、在正确实现上会绿，这样我能确认它测的是真东西。
19. 作为读流水线日志的人，我希望失败信息直接说出「宿主为什么没看见我们」（声明缺失 / 平台不是网页 / 客户端产物路径取不到 / 产物文件不存在），而不是只说一个断言失败。
20. 作为读流水线日志的人，我希望复验在「这个版本还没发布」时给出明确结论并退非零，而不是抛一个 registry 404 的栈。

### 迁移与共存

21. 作为一个仍在用旧包的使用者，我想让两个包共存而不互相踩，这样我可以先并排试再决定切不切。
22. 作为一个关心技能正文出处的使用者，我想看到技能来源被钉在某个上游版本上，这样我知道它不会在半夜自己变。
23. 作为一个要把它写进公司内部清单的人，我想要一个稳定的默认标签与可引用的版本号，这样我的清单不会指向一个不存在的包。
24. 作为后来接手这个仓库的人，我希望规格里能写清「为什么不做到界面那一层」，这样我不会以为那是漏掉的活。

## Implementation Decisions

### 一、发布本身

- **发布入口只有包管理器的发布命令，且必须吃发布前钩子。** 当前发布前钩子串的六道门保留原样，不加不减。文档与脚本里都不得出现跳过生命周期脚本的开关；要跳过，唯一合法做法是把门改好，不是把门关上。
- **兼容矩阵那道门依赖网络。** 发布机上必须有网。仓里那张离线已知版本表只是「拿不到 registry 时退回」的缓存，不能当成发布前的替代——带校验参数运行时会重取并比对。
- **发布前先确认这个包名在 registry 上还没有该版本**，避免误覆盖；发布后再读一次 registry 上该版本的完整性摘要与压缩包地址做核对。这一步写进发布清单，不写进脚本：发布一旦成功就不可逆，脚本里加「先查再发」反而给了绕过检查的缝隙。
- **默认标签指向 0.2.0。** 首次发布，没有历史标签需要迁移。将来发补丁版是常规动作，本规格不预设标签策略。
- **不拿试运行当作验收依据。** 试运行不触发发布前钩子，绿了也说明不了六道门过了——它只能回答「文件清单对不对」。真正的清单验收已经在流水线的打包作业里逐条核对。
- **失败时的收场动作**：撤回在发布后七十二小时内可用，但**默认不撤回**——已经有人装过再撤回会破坏别人的锁文件。正解是发一个补丁版修好并让默认标签前进。这条写进发布清单的「出事了怎么办」。
- **不使用出产地签名。** 它要求从托管流水线发布且仓库托管在公共代码托管平台，而当前工作目录不是 git 仓库、没有远端。列为后续；现在的验收是「署名信息各项必须为空」。

### 二、发布后复验（从 registry 拉回真实字节）

- **复验的输入必须是 registry 上那份压缩包，不是本地那份。** 做法是从 registry 打包到临时目录（带版本的打包命令会走网络），不落依赖目录、比安装更快。
- **完整性核对用 registry 记录的哈希**，与本地打包产物用同一套哈希算法（都用包管理器自己算的，不自己拼摘要）。两侧算法必须同源。
- **复验复用现有装置，不新造**：装配探针已经在临时目录里做「装进去 → 六个技能 → 切档 → 用户目录零垃圾」四段断言，复验就是把输入源换成 registry 的那份压缩包。探针已有的压缩包输入参数直接可用，**不新增参数面**。
- **复验脚本要能被单独跑**：新增一条包脚本（发布后手动或流水线手动触发），不属于发布前钩子（发布前包还不存在）。它在版本不存在时必须给出「这个版本还没发布」的明确结论并退非零，而不是抛 registry 404 的栈。

### 三、「宿主看见我们」的机器证据（接缝已实测可行）

- **接缝只有一条：装配探针起的那棵真 cordis 树。** 在装载器起完、插件装载完之后，把宿主自己的客户端模块登记服务挂上去，然后读它的公开面。这是最高可行接缝：输入是真装好的包，输出是宿主自己的判定结果，中间不经过我们写的任何解析逻辑。
- **为什么不选更低的接缝**（直接读清单判形状）：那正是现有的清单形状测试在做的事，它证明不了「宿主认不认」——清单对而宿主丢包的三种成因它一条都覆盖不到。
- **为什么不选更高的接缝**（真宿主进程加浏览器调试协议看界面）：设置页槽位的声明方是另一个包，它在目标环境里存不存在是**用户环境的事实**；在临时环境里复现整套客户端运行时（渲染器、设置页、设置页通用项、基础组件、页面种子模块）成本极高，换来的是一张只对某个宿主版本成立的截图。边界到此为止，写进说明文档的常见问题。
- **树的形态有硬约束**：登记服务的静态注入声明要求装载器先起来，所以必须排在装载器之后挂载；它的构造函数里对网页服务器是可选注入，没有网页服务器时静默等待、不报错——这一点已实测（真树里无网页服务器，登记服务正常构造并给出正确结果）。
- **断言内容五条**：
  1. 登记服务的模块图条目里包含本包（能按包名找到）；
  2. 按包名取客户端产物路径不返回空，且该路径在磁盘上真实存在；
  3. 发现函数对「装载器里这一行的模块名」返回非空结果；
  4. 结果里的平台是网页；
  5. 结果里的外部依赖是数组（可以为空），且客户端产物路径与第 2 条取到的是同一个文件。
- **客户端产物路径的比对必须先做真实路径规约**。实测：临时目录的路径经规约会从一条短前缀变成一条长前缀，直接字符串比对会假红。这与越界防护那张票踩过的是同一个坑。
- **产物外壳的判定要放宽**。实测产物前两行是生成说明注释，模块装载外壳出现在第三行；断言必须是「文件里存在这个外壳且标识等于包名」，不是「首行是它」。
- **反向用例是必须的，且已经实测过五种形态**：原样有结果；删掉客户端声明返回空；平台改成非网页返回空；删掉导出映射里的客户端入口抛「声明了客户端入口但导不出产物」；恢复原样又有结果。这条走装配探针已有的自检机制，与现有反向用例同构。
- **失败文案要说出成因**，不能只说断言失败：声明缺失、平台不是网页、导出映射缺客户端入口、产物文件不存在，四种要给四种话。

### 四、清单与文档的最小改动面

- 包清单只在需要时补发版必需的元数据（仓库地址、主页、问题跟踪、作者），**不改**已验收的五个字段：文件白名单、导出映射、宿主引擎区间、宿主对等依赖、宿主声明段。它们各自有测试或流水线卡口钉住，动一下就要连带改测试。
- 新增字段必须是包管理器的官方字段名，不接受自定义键。
- **说明文档的安装段改成「按包名装」**，把压缩包手工安装降级为「离线 / 内网」备选路径，并写清那条路的已知边界（离线安装时对等依赖不会被自动补装，需要提前备好）。当前说明文档只描述手工路径，会让第一个陌生用户卡住。
- **变更日志不新增版本段**：0.2.0 那段已在，发布不改变包的内容。若发布过程中改了任何字节，那是补丁版而不是把 0.2.0 改一遍。

### 五、与既有装置的关系（不重造）

- 六道质量门、装配探针的三种形态、清单与源码的双向联动检查、清单形状测试，**全部保留原样**。本规格只新增：一条复验脚本、装配探针里一段五条断言、发布清单文档、说明文档安装段改写。
- **不新增第二套装配装置。** 复验需要的那段逻辑就长在装配探针里，不要另起脚本——两套装置迟早会漂。

## Testing Decisions

**什么算好测试**：只断言外部可观察的行为，不断言实现细节。具体到本轮：

- 「发了」等于 registry 上能查到那个版本，不是「我们跑了发布命令」。
- 「装得上」等于从 registry 拉下来的字节能被加载，不是「本地压缩包能被加载」。
- 「宿主看见了客户端入口」等于宿主的发现函数返回了一个非空、产物路径指向真文件的结果，不是「我们的清单里有那个键」。

**接缝——只有一条，需要确认**：

| 项 | 内容 |
|---|---|
| 接缝 | 装配探针起的那棵真 cordis 树（装载器 + 装载器内建 + 装好的本包） |
| 输入 | 临时环境里装好的包目录（不是仓库工作区） |
| 输出 | 宿主客户端模块登记服务的公开面：模块图、按包名取产物路径、发现函数 |
| 覆盖的失败模式 | 声明缺失 / 平台不对 / 导出映射缺客户端入口 / 产物文件不存在 / 模块图里没这一行 |
| 明确不覆盖 | 设置页槽位声明方缺席、权限不足、真实界面渲染 |

选它而不是别处的理由：这是能同时看见「我们的产物」与「宿主的判定」的最高点，且不引入任何新的运行时依赖——那棵树的起法已经在用，只需多挂一个服务。

**要测的模块与对应用例**：

1. **装配探针新增段（本轮唯一新增的测试面）**：五条正向断言加五种反向形态，夹具是「刚装好的临时环境」。
2. **复验脚本本身**：给它一个不存在的版本，必须给出「未发布」结论并退非零（纯离线可测）；给它已发布版本，必须走完装配四段（需网络）。
3. **清单形状测试不动**。它管「仓内清单形状」，与本轮的「发布字节被宿主接受」是两件事，混在一起会让失败原因变模糊。

**先例（都在仓内）**：

- 装配探针的自检机制：把技能目录清空后装配必须报红，证明断言不是装饰。本轮的「删掉客户端声明必须红」照抄这个形状。
- 产物校验脚本的自检（十九条）：给每个检查配一对正反用例。本轮的宿主发现断言必须配反例，理由相同。
- 越界防护那批测试的「缺陷版先红、修复版后绿」取证法：先把实现短路成错误版本跑一次，确认变红，再恢复。本轮的反向用例照这个做，两次输出都贴进实施票。
- 装配探针现有的「四档提示词体量」断言：它证明的不只是「装上了」，而是「装上了且真的在工作」。本轮的「产物路径指向真文件」是同一类断言。
- 已实测的反向五态与真树正向结果，见进一步说明里的探针记录——这条接缝不是设想，是跑通过的。

## Out of Scope

- **界面渲染断言、截图比对、视觉验收。** 槽位声明方是否存在于目标环境是用户环境的事实；复现整套客户端运行时的成本与收益不成比例。
- **出产地签名。** 要求从公共代码托管平台的流水线发布——这条前置现在**已具备**（`58fly/dsh-ponytail-58fly` 是公开 GitHub 仓库，`.github/workflows/publish.yml` 也在），但本轮仍不做：它会在 registry 上写 attestation，与「署名信息各项为空」这条验收直接冲突。要不要开是独立决定，列后续。
- **自动发版流水线**（打标签触发、自动版本号）。本轮是首次手工发布，先把「一次发布做对」走通。
- **撤回自动化。** 撤回是人工决策，不能写成脚本默认动作。
- **发布标签策略**（预发布通道）。首次发布只有一个默认标签。
- **技能正文与上游同步。** 那是技能校验的漂移作业的职责，与发布无关。
- **修改任何已验收的清单字段。**

## Further Notes
